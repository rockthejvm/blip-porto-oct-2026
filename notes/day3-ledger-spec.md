## 1. Context

Daniel from Rock the JVM is running a 3-day intensive Scala training for professional software engineers. Day 1 is language fundamentals, day 2 is FP exercises (collections, error handling, ADTs), and day 3 is a full-day team project. This spec covers day 3.

Students work in teams of 2–3 for roughly 9:00–17:00. They receive a skeleton repository and build an event-sourced account ledger against a fixed text protocol, passing progressively harder milestone tests.

**Explicit constraint from the trainer:** heavy FP, idiomatic Scala, but *no fancy language features*. No higher-kinded types. No typeclass derivation. No `given`/`using` beyond what a test framework needs internally. No cats, no ZIO, no fs2, no third-party libraries at all beyond the test framework. FP here means: algebraic data types, exhaustive pattern matching, immutability, total functions, folds, `Option`/`Either`, and function composition. If you find yourself wanting `F[_]`, you have gone wrong.

## 2. What the students are building, and why

### The project

A command-line ledger for bank accounts. It reads a scenario file of commands (`OPEN`, `DEPOSIT`, `WITHDRAW`, `TRANSFER`, `BALANCE`, ...), one per line, and prints a response for each. Accepted commands produce events; rejected commands produce a rejection line. Accepted events are appended to a journal file, and the entire application state can be rebuilt from that journal alone.

### The pedagogical spine

The whole engine is two pure functions:

```scala
def decide(state: State, cmd: Command): Either[Rejection, List[Event]]
def evolve(state: State, event: Event): State
```

`decide` validates and may refuse. `evolve` is total, unconditional, and never fails — it merely applies something that has already happened. Application state is `events.foldLeft(empty)(evolve)`.

Three things follow from this, and they are the entire teaching payload of the day:

1. **Commands and events are different types.** A command is a request that can be refused; an event is a fact that already happened. Most teams will initially model them as one type. This is the single most valuable mistake in the project — it breaks visibly at M2 (validation would have to re-run on replay) and again at M4 (one command emits two events).
2. **State is a fold.** Once they see `foldLeft(evolve)`, the day-2 material on folds retroactively acquires a point.
3. **Purity localizes effects.** File I/O appears in exactly one object, at the edge. Everything else is testable with no mocks, no fixtures, and no setup.

### What "done" looks like for a student team

A working ledger that survives restart, handles transfers atomically across two accounts, rejects every invalid operation with a precise reason, and answers historical queries over its own event log — with a data model they designed themselves and a test suite that passes end to end. That is a realistic artifact; the same command/event/fold shape appears in CQRS systems, Akka persistence, Redux reducers, and most financial back-ends.

### 5.1 Scenario tiers

Every milestone gets the same five-tier ladder. The tiers exist because a student debugging a failure needs a small file, and a grader needs a big one.

| Tier | Files | Length | Purpose |
|---|---|---|---|
| easy | 1–2 | 8–20 lines | Happy path, one or two accounts. First thing a team gets green. |
| medium | 1–2 | 40–80 lines | Every rule in the milestone exercised at least once. Hand-verifiable in a few minutes. |
| large | 1 | 100–200 lines | Interleaved accounts, rules in combination, ordering edge cases. Still readable under duress. |
| huge | 1 | 1000+ lines | Machine-generated. Never read by a human. The real gate. |

Authoring rules:

- **easy, medium, and large `.in` files are hand-written.** Author them deliberately so each one has a stated purpose, and put that purpose in a `#` comment header. Their `.out` files are generated by the reference solution and then hand-reviewed line by line.
- **huge `.in` files are generated** by `/scripts/gen-huge.scala`, a seeded generator with a hard-coded seed per milestone. Same seed must produce a byte-identical file forever; commit both `.in` and `.out`. The generator must be milestone-aware — `m2_huge.in` may not contain `TRANSFER` — and must be weighted to produce a realistic mix: roughly 55% accepted commands, 30% rejections spread across every reason, 10% queries, 5% malformed lines. It must also guarantee coverage: assert before writing that every rejection reason and every `ERROR` variant appears at least twice in the generated file.
- **Cumulative, not isolated.** Every milestone's tiers include the previous milestone's commands. `m4_large.in` should contain deposits and freezes alongside transfers, so regressions surface immediately.
- **Tag the huge scenarios** so `sbt test` runs the fast tiers by default and `sbt "testOnly * -- --include-tags=huge"` (or a `slow` munit tag) runs the full set. Students will run the fast set forty times an hour; a 1000-line diff in that loop is a waste of their day.
- **Truncate diffs on huge failures.** `GoldenSpec` must print at most the first 5 differing lines plus a total count. Never dump a 1000-line diff into the console.

Ship all tiers in the student handout — teams should be able to run their own final gate. The hidden grading set (§10) is separate and additional.

## 6. The pinned interface and harness

This is the only contract between the student's model and the test harness. Keep it this small — one type parameter, no HKTs, no constraints.

`LedgerEngine.scala`:

```scala
package ledger

/** The single contract between your ledger and the test harness.
  *
  * `S` is YOUR state type. The harness never inspects it; it only threads it
  * through. Everything about your data model is your decision.
  */
trait LedgerEngine[S]:
  /** The state of a ledger that has seen no events. */
  def empty: S

  /** Handle one raw input line.
    *
    * Returns the new state and the response lines to print, in order.
    * This function must be pure: same state + same line => same result,
    * always, with no I/O and no mutation.
    */
  def execute(state: S, line: String): (S, List[String])
```

`Harness.scala`:

```scala
package ledger

object Harness:
  /** Run every input line through the engine, threading state.
    *
    * This is the whole application. Note what is NOT here: no vars, no
    * mutation, no I/O. The state of the system is a fold over its inputs.
    */
  def run[S](engine: LedgerEngine[S], input: List[String]): List[String] =
    input
      .foldLeft((engine.empty, List.empty[String])) { case ((state, out), line) =>
        val (next, responses) = engine.execute(state, line)
        (next, out ++ responses)
      }
      ._2

  /** Same, but starting from a state that was rebuilt from a journal. */
  def runFrom[S](engine: LedgerEngine[S], start: S, input: List[String]): List[String] =
    input
      .foldLeft((start, List.empty[String])) { case ((state, out), line) =>
        val (next, responses) = engine.execute(state, line)
        (next, out ++ responses)
      }
      ._2
```

`MyLedger.scala` (the stub students replace):

```scala
package ledger

/** Your implementation. Replace `Unit` with your own state type. */
object MyLedger extends LedgerEngine[Unit]:
  def empty: Unit = ()
  def execute(state: Unit, line: String): (Unit, List[String]) =
    ((), List("ERROR NotImplemented"))
```

`Main.scala` reads a scenario file, runs the harness, prints results, and handles the `--journal` flag (§9). Provide it complete.

## 7. The text protocol

**This section is the specification the golden files enforce. It must be implemented exactly, by both the reference solution and the students. Be pedantic here — every ambiguity you leave becomes a team stuck for 20 minutes on whitespace.**

### 7.1 Input

One command per line. Fields separated by one or more spaces. Leading/trailing whitespace on a line is stripped. Blank lines and lines whose first non-space character is `#` produce **no output at all**.

Verbs are uppercase. Account ids match `[a-z0-9-]{1,32}`. Currency codes are three uppercase letters; supported currencies are `USD`, `EUR`, `GBP` — all with two decimal places. (JPY and other zero-decimal currencies are deliberately out of scope; note this in the student README so nobody rabbit-holes.)

| Command | Arity | Milestone |
|---|---|---|
| `OPEN <acc> <CUR>` | 2 | M1 |
| `DEPOSIT <acc> <amount>` | 2 | M1 |
| `BALANCE <acc>` | 1 | M1 |
| `WITHDRAW <acc> <amount>` | 2 | M2 |
| `FREEZE <acc>` | 1 | M2 |
| `UNFREEZE <acc>` | 1 | M2 |
| `CLOSE <acc>` | 1 | M2 |
| `TRANSFER <from> <to> <amount>` | 3 | M4 |
| `HISTORY <acc>` | 1 | M5 |
| `SUMMARY <acc> <fromSeq> <toSeq>` | 3 | M5 |

### 7.2 Money

Input amounts match `-?\d+(\.\d{1,2})?`. So `100`, `100.5`, `100.50`, and `-5.00` all **parse successfully**. Three or more decimal places (`1.005`) is a parse failure.

Output amounts are always rendered with exactly two decimal places and no thousands separators: `0.00`, `100.00`, `1234567.89`. Negative amounts render with a leading `-`.

Internally money must be an integer minor-unit count (`case class Money(cents: Long)` or equivalent). Students who reach for `Double` must be redirected — this is a scheduled teaching moment at the model review, not something the skeleton prevents.

**Note the deliberate design choice:** a negative amount *parses*, and is then rejected by `decide` as `non-positive-amount`. Parsing is dumb; validation lives in one place. Call this out in the instructor notes — students often want to reject negatives in the parser, and the reason not to is that the parser has no access to state and no rejection vocabulary.

### 7.3 Output — accepted commands

**Design rule for this whole section, and the reason it looks the way it does: the wire format is a lossy projection of the event log, not a rendering of it.** It never names an event. It describes the observable consequence of one. This is deliberate — if the output named events one-for-one, a team could transcribe the protocol document into an `enum Event` in four minutes and skip the modeling exercise that is the point of the day. Do not "improve" this by making the output more self-describing.

Every accepted command produces one line per recorded fact:

```
OK <seq> <acc> <effect>
```

`<seq>` is a **global, 1-based, monotonically increasing sequence number** covering every fact the ledger has ever recorded, across all accounts. It never resets, never has gaps, and is never assigned to a rejected command, a query, or a malformed line.

`<effect>` is one of:

| Effect | Meaning |
|---|---|
| `OPENED <CUR>` | an account came into existence |
| `+<amount> <balance>` | a credit, followed by the resulting balance |
| `-<amount> <balance>` | a debit, followed by the resulting balance |
| `FROZEN` | account is now frozen |
| `UNFROZEN` | account is now not frozen |
| `CLOSED` | account is now closed |

Worked example:

```
OPEN acc-1 USD             →  OK 1 acc-1 OPENED USD
DEPOSIT acc-1 100.00       →  OK 2 acc-1 +100.00 100.00
DEPOSIT acc-1 25           →  OK 3 acc-1 +25.00 125.00
WITHDRAW acc-1 30.00       →  OK 4 acc-1 -30.00 95.00
FREEZE acc-1               →  OK 5 acc-1 FROZEN
UNFREEZE acc-1             →  OK 6 acc-1 UNFROZEN
```

A successful `TRANSFER` produces exactly two lines, debit first, sharing a transfer tag:

```
OK 7 acc-1 -50.00 45.00 xfer=t1
OK 8 acc-2 +50.00 50.00 xfer=t1
```

`<tid>` is `t` followed by a 1-based counter of *successful* transfers in this ledger's history.

Three properties of this format are load-bearing. Preserve all three:

1. **Credits and debits render identically as signed adjustments.** The wire cannot tell you whether the model has one `Adjusted(delta)` event or two separate `Deposited`/`Withdrawn` events. Both are defensible designs; the choice stays the students'.
2. **The sequence number forces an append-only log.** You cannot produce a correct global `<seq>` without an event history, so the log is mandatory from M1 without ever being described. This is what stops a team from building a pure state-mutation model that passes M1 and M2 and then needs a rewrite at 14:00.
3. **The resulting balance in every adjustment line forces the fold immediately.** M1 cannot be faked with string manipulation.

`OPENED`, `FROZEN`, `UNFROZEN`, and `CLOSED` do name lifecycle *states*. That is unavoidable — the states are requirements. Note that a state name is not an event name, and how status is represented (a `Status` enum, two booleans, a nested ADT) remains an open modeling decision worth raising at the review.

### 7.4 Output — rejections

Exactly one line, never more:

```
REJECTED unknown-account account=<acc>
REJECTED account-exists account=<acc>
REJECTED unsupported-currency currency=<CUR>
REJECTED account-closed account=<acc>
REJECTED account-frozen account=<acc>
REJECTED non-positive-amount account=<acc> amount=<amount>
REJECTED insufficient-funds account=<acc> balance=<amount> requested=<amount>
REJECTED same-account-transfer account=<acc>
REJECTED currency-mismatch from=<acc> to=<acc> from-currency=<CUR> to-currency=<CUR>
REJECTED non-zero-balance account=<acc> balance=<amount>
```

Key-value pairs appear in exactly the order shown, single-spaced, no spaces around `=`.

**Codes are kebab-case on purpose.** `insufficient-funds` is not a legal Scala identifier, so the wire vocabulary cannot be pasted into an `enum` — a render function from the student's own rejection type to these codes is mandatory. Be honest in the instructor notes about how far this goes: it blocks transcription, not knowledge. The *set* of failure conditions is a requirement and cannot be hidden from anyone asked to implement it. What stays open is the structure behind the codes — one flat enum or several grouped ones, whether the payload data lives in the case or is computed at render time, whether `insufficient-funds` and `non-zero-balance` share a common shape.

### 7.5 Rejection precedence

When several rejections apply, exactly one is emitted, chosen by this order. **This must be specified and taught, not discovered** — ordering of validation is a spec decision, and golden files are ambiguous without it.

Single-account commands (`DEPOSIT`, `WITHDRAW`, `FREEZE`, `UNFREEZE`, `CLOSE`, `BALANCE`, `HISTORY`, `SUMMARY`):

1. `unknown-account`
2. `account-closed`
3. `account-frozen`
4. `non-positive-amount`
5. `insufficient-funds`
6. `non-zero-balance`

`OPEN`: `account-exists` before `unsupported-currency`.

`TRANSFER`, evaluated in this exact order:

1. `same-account-transfer` (checked before either account is looked up)
2. `unknown-account` on source
3. `unknown-account` on destination
4. `account-closed` on source
5. `account-closed` on destination
6. `account-frozen` on source
7. `account-frozen` on destination
8. `non-positive-amount` (`account=` is the source)
9. `currency-mismatch`
10. `insufficient-funds` (`account=` is the source)

Additional rules:
- `FREEZE` on an already-frozen account and `UNFREEZE` on a non-frozen account are **idempotent successes** — they record a fact and emit an `OK` line normally, consuming a sequence number. (Whether that is the right design is a good discussion; the spec keeps it simple.)
- `CLOSE` requires a zero balance; otherwise `non-zero-balance`.
- Every command on a closed account is rejected, including `BALANCE` and `DEPOSIT`. Closure is terminal — there is no reopen, and re-`OPEN`ing a closed id yields `account-exists`.
- A frozen account rejects `DEPOSIT`, `WITHDRAW`, and transfers in either direction, but permits `BALANCE`, `HISTORY`, `SUMMARY`, `UNFREEZE`, and `CLOSE`.

### 7.6 Output — queries

Queries never record facts and never consume sequence numbers.

```
BALANCE <acc> <amount> <CUR>
```

`HISTORY` is a projection over the account's facts, reusing the exact `<effect>` grammar from §7.3:

```
HISTORY <acc> <count>
  <seq> <effect>
  <seq> <effect>
```

Detail lines are indented exactly two spaces and are ordered by ascending `<seq>`. An account with no facts prints only the header with count `0`. Example for the worked sequence above:

```
HISTORY acc-1 7
  1 OPENED USD
  2 +100.00 100.00
  3 +25.00 125.00
  4 -30.00 95.00
  5 FROZEN
  6 UNFROZEN
  7 -50.00 45.00 xfer=t1
```

Reusing the effect renderer across `OK` lines and `HISTORY` lines is intentional: one rendering function, two call sites, and a visible payoff for having separated rendering from the model.

`SUMMARY <acc> <fromSeq> <toSeq>` aggregates over an inclusive window of global sequence numbers and prints a single line:

```
SUMMARY <acc> <fromSeq> <toSeq> opening=<amount> credits=<amount> debits=<amount> closing=<amount> count=<n>
```

- `opening` is the account's balance after all of its facts with `seq < fromSeq`, or `0.00` if there are none.
- `credits` and `debits` are sums over this account's facts within the window.
- `closing` = `opening + credits - debits`, and must also equal the balance after all facts with `seq <= toSeq`. The reference solution should compute it both ways and assert they agree; that assertion is a free property test.
- `count` is the number of this account's facts within the window, including non-financial ones.
- A window that contains no facts for the account is valid and prints zeros with `opening` = `closing` = the account's balance at `fromSeq`.

This is a fold over a filtered log with a case-class accumulator, which is exactly the M5 teaching target.

### 7.7 Output — malformed input

```
ERROR unknown-command <verb>
ERROR bad-arguments <verb>
ERROR bad-account-id <token>
ERROR bad-amount <token>
ERROR bad-currency <token>
ERROR bad-sequence <token>
ERROR bad-range <fromSeq>-<toSeq>
```

Precedence within a line: unknown verb first, then arity, then argument parsing left to right. `<verb>` is echoed exactly as it appeared, including wrong case — so `deposit acc-1 5` yields `ERROR unknown-command deposit`. Sequence arguments to `SUMMARY` must match `\d+`, else `bad-sequence`; `fromSeq > toSeq` yields `bad-range`. Malformed lines never record facts, never consume sequence numbers, and never touch the journal.

## 8. Golden-file test harness

`GoldenSpec.scala` discovers every `scenarios/*.in` that has a sibling `.out`, runs it through `Harness.run(MyLedger, lines)`, and asserts line-by-line equality. Requirements:

- Group by milestone prefix so students can run `sbt "testOnly *GoldenSpec* -- *m2*"` or equivalent; munit tags or per-file test names are fine, but the filtering must be documented in the README.
- On failure, print a **unified diff with line numbers**, showing the first differing line prominently. Do not dump two 60-line blocks and leave them to eyeball it. This matters more than it sounds — it is the difference between a 2-minute fix and a 15-minute one, forty times over the day.
- Trailing whitespace on both sides is stripped before comparison. A trailing newline at end of file is not significant.
- Scenarios whose `.out` file is missing are skipped silently (they belong to `ReplaySpec`).

## 9. Persistence and the replay property (M3)

The journal format is the student's choice — that is part of the exercise. The tests must therefore verify replay **without ever seeing the journal file's contents**.

Do it with a replay-equivalence property:

> Running scenario `A` then scenario `B` against a shared journal, with a process restart in between, must produce the same output for `B` as running `A ++ B` in a single fresh process produces for its `B` portion.

`ReplaySpec` implements this by:
1. Running `m3_replay_a.in` against a temp journal path, discarding output.
2. Constructing a fresh engine state by loading that journal.
3. Running `m3_replay_b.in` from that state, capturing output.
4. Running `m3_replay_a.in ++ m3_replay_b.in` in one pass from `empty`, capturing output and dropping the first N lines corresponding to A.
5. Asserting the two B-outputs are equal.

To make step 2 possible through the pinned interface without exposing the student's `Event` type, extend the contract minimally in the M3 section of `MILESTONES.md` with a second small trait, provided in the skeleton:

```scala
package ledger

/** Implemented at M3. The only place in your program where I/O is allowed. */
trait JournaledLedger[S] extends LedgerEngine[S]:
  /** Serialize newly-produced events to append to the journal.
    * Called by Main after each accepted command. Format is your choice.
    */
  def journalLines(before: S, after: S): List[String]

  /** Rebuild state by replaying journal lines written by `journalLines`. */
  def replay(lines: List[String]): S
```

Note `journalLines(before, after)` deliberately avoids naming the event type. If you find a cleaner signature that preserves that property, use it, but do not introduce a type parameter for events — that pushes toward `LedgerEngine[S, E]` and then toward abstraction the trainer has ruled out.

Design the `m3_replay_*.in` pair to catch both counter traps, which are the whole point of this milestone's scenarios:

- **The sequence counter.** A team holding `<seq>` in a mutable variable, or deriving it from "facts recorded this run" rather than from the full history, restarts at 1 after replay. Scenario A must record at least a dozen facts and B must record more, so a reset is glaringly visible in the diff.
- **The transfer counter.** Same failure, one level subtler: A must contain at least one successful transfer and B another, so a `var`-held counter emits `t1` twice.

Both counters must be derived from the event history. Leave both traps in; they are the cheapest available demonstration that state is a fold over the log rather than something accumulated on the side.

### Stretch goals

List these in `MILESTONES.md` for fast teams, in this order:

1. Two-phase transfer — `TransferInitiated` / `TransferCompleted` / `TransferFailed`, with rollback when the destination rejects.
2. Snapshots — persist `(state, seq)` so replay does not start from event zero; the replay-equivalence property must still hold.
3. Optimistic concurrency — an `expectedVersion` field on commands, rejected as `REJECTED version-conflict account=<acc> expected=<n> actual=<n>`.
4. Property tests — money conservation across transfers, replay determinism, `<seq>` density (no gaps, no repeats), and `evolve` totality over all events `decide` can emit.
5. A small query ADT interpreted over the event log.

Stretch goals need no golden scenarios; they are demo material.

### Hidden grading set

In `/instructor/hidden-scenarios/`, produce a parallel set that students never see, exercising the same milestones with nastier inputs: interleaved accounts, rejection-precedence edge cases (frozen *and* insufficient funds, closed *and* unknown), transfers between accounts of different currencies where both are also frozen, `CLOSE` with a non-zero balance followed by `WITHDRAW` to zero then `CLOSE` again, malformed lines interleaved with valid ones so that sequence numbers must *not* advance across them, `SUMMARY` windows that start mid-transfer (`fromSeq` falling between a transfer's two facts), `SUMMARY` windows containing no facts for the account, and a scenario where the same account id is opened, closed, and re-opened (which must be rejected).

Provide `/scripts/grade.sh <team-repo-path>` that copies the hidden scenarios in, runs the suite, and prints a per-milestone pass/fail table.

## 11. Student-facing documents

### `student/README.md`

Cover, in this order: what they are building in two paragraphs; the `decide`/`evolve` framing shown as bare signatures with no accompanying types; the constraint list (stdlib + munit only, no cats/ZIO, no HKTs, no givens); how to run the app and the tests; how to filter tests by milestone; where their code goes (`domain/`, plus replacing `MyLedger`); the instruction to design the data model on paper before touching a keyboard; and a pointer to `PROTOCOL.md`.

### `student/PROTOCOL.md` and `student/PROTOCOL-PART2.md`

**The protocol is handed out in two stages.** `PROTOCOL.md` covers §7.1–7.5 and §7.7 for M1–M3 commands only: `OPEN`, `DEPOSIT`, `WITHDRAW`, `BALANCE`, `FREEZE`, `UNFREEZE`, `CLOSE`. `PROTOCOL-PART2.md` covers `TRANSFER`, `HISTORY`, and `SUMMARY`, and is handed out after lunch.

## 14. Model review checklist (for `MODEL_REVIEW.md`)

Failure modes to catch at 10:10, with the question that surfaces each without giving the answer away:

- **One type for commands and events.** → "What goes in the log when a withdrawal is refused?"
- **`Double` for money.** → "Compute 0.1 + 0.2 in the REPL."
- **Validation inside `evolve`.** → "What happens when you replay a log written last Tuesday?"
- **`var` state, or `mutable.Map` of accounts.** → "How would you implement undo?"
- **`decide` returning a single `Event`.** → "How many things happen during a transfer?" (Do not tell them M4 is coming; let the refactor land.)
- **Premature abstraction** — someone will propose `trait Aggregate[C, E, S]` around 10:15. → "Make one concrete case work first." Note that this is also precisely the abstraction the trainer excluded from the course.
- **Balance stored as a field and also derivable from events.** → "Which one is the truth?" (Either answer is defensible; the point is that they choose deliberately.)
- **String-typed rejections.** → "How does the caller distinguish two of them?"
- **A model shaped like the wire format** — an `Effect` type with a `sign` and an `amount`, mirroring the output lines. → "If we changed the output format tomorrow, how much of your model changes?" The wire is a projection; a model that is isomorphic to it has skipped the modeling.
- **No event type at all**, just a `Map[String, Account]` mutated per command. → "Where does the sequence number come from?" This usually surfaces within ten minutes of M1 starting rather than at the review; catch it early, because it is the one mistake that costs a rewrite rather than a refactor.

## 15. Debrief points (for `TEACHING_NOTES.md`)

Close the loop by naming where this shape appears in production systems: CQRS/event sourcing generally, Akka/Pekko persistent actors, Redux and React reducers, Kafka log compaction, and double-entry accounting itself, which has worked this way since the fifteenth century.

Then name the honest tradeoffs, because they will meet all three in real code: replay cost without snapshots; event schema evolution and versioning; and eventual consistency of projections as an operational problem, not a theoretical one.

Finish on the day-2 callback: the reason any of this worked is that state is immutable and the transition is a total function, which is why `foldLeft` was sufficient for the entire application.
